## ЧТО ЗА ПРОДУКT

**MAS Platform** — облачная мультиагентная система автоматизации маркетинга и
операций. Это коммерческий **B2B SaaS**: набор ИИ-агентов, которые выполняют
маркетинговые задачи для бизнеса (агентств, локального бизнеса), работающего
с российским рынком. Система мультитенантная — один экземпляр обслуживает
много клиентов-компаний («тенантов»), у каждого свой профиль бренда и данные.

Задачи, которые автоматизирует система (по периодичности):
- **Ежедневно:** контроль лидов (сверка звонков/заявок Calltouch с CRM),
  автопостинг согласованного контента.
- **Еженедельно:** отчёт по рекламному трафику, финансовая сверка (сметы ↔ сделки),
  контент недели (посты), рассылки (SMS/WhatsApp), ТЗ дизайнеру.
- **Ежемесячно:** анализ конкурентов, контент-план, УТП, обновление гео-сервисов.

**Ключевой принцип «честной автоматизации»:** LLM (нейросеть) используется ТОЛЬКО
для работы с языком (генерация текстов, анализ, интерпретация). Всё, что связано
с деньгами и данными (сверка лидов, финансов, публикация) — это
**детерминированный код без LLM**, чтобы исключить галлюцинации в критичных операциях.
Между генерацией контента и публикацией всегда стоит **согласование человеком**
(human-in-the-loop).

## СТЕК ТЕХНОЛОГИЙ

- **Язык:** Python 3.11+
- **Веб-бэкенд:** FastAPI + Uvicorn, шаблоны Jinja2 (серверный HTML, без React пока)
- **Оркестрация агентов:** LangGraph (графы состояний с условными переходами и циклами)
- **База данных:** SQLite (в режиме WAL). В перспективе — миграция на PostgreSQL.
- **Планировщик:** APScheduler (локальная замена Celery Beat из спецификации)
- **LLM-шлюз:** единая точка `app/llm.py` с автовыбором:
  Ollama (локально, qwen2.5:7b — режим разработки) → GigaChat (облако, Сбер —
  так работает сервер) → черновой режим (заглушки, агенты не падают).
- **Уведомления/публикация:** Telegram Bot API
- **Google Sheets:** gspread (чтение смет; запись УТП и ТЗ дизайнеру)
- **Хостинг:** VPS на Ubuntu 24.04, службы systemd, доступ через Cloudflare Tunnel.

      traffic.py       # Аналитик трафика: реальные звонки Calltouch, аномалии (код) + LLM
      leads.py         # Контроль лидов: полная сверка Calltouch↔CRM (детерминированно)

**Цепочка агентов (важно понимать связи).**
`Анализ конкурентов` → его отчёт читает `Контент-план` (db.last_run_output) →
темы попадают в таблицу content_plan → по ним `ТЗ дизайнеру` делает задания на
макеты, а `Контент недели` пишет посты → посты идут в очередь согласования →
после кнопки человека `Публикатор` постит в Telegram-канал.

**Как работают агенты (общий паттерн).** Каждый агент — функция `run(tenant_id)`.
Она: (1) берёт данные тенанта и настройки из БД, (2) выполняет работу
(детерминированную и/или через LLM), (3) пишет результат в таблицу `agent_runs`
и/или `generated_content`, (4) шлёт уведомление в Telegram. Запускается либо
кнопкой в веб-панели (в фоне через BackgroundTasks), либо планировщиком по расписанию.

**Веб-панель.** Вход по паролю (middleware закрывает все страницы, кроме /login).
Разделы: **Обзор** (плитки показателей, график активности за неделю, чек-лист
первичной настройки, клиенты, последние запуски), **карточка клиента** (кнопки
агентов + «Запустить все проверки», интеграции, профиль бренда, контент-план,
конкуренты), **Контент** (очередь согласования), **Журнал** (+ полный отчёт по
клику), **Ключи** (загрузка google_key.json через браузер).
Дизайн — единая система в `templates/base.html`: карточки, плитки, бейджи статусов
(всегда значок + подпись, не только цвет), плашки-подтверждения после действий.
В подвале — версия и коммит сборки: сразу видно, доехал ли деплой на сервер.

**Мультитенантность.** Всё привязано к `tenant_id`. Профиль бренда клиента
(tone of voice, стоп-слова, слова-призывы) хранится в БД как JSON и подмешивается
в промпты агентов — поэтому один код пишет по-разному для разных клиентов.

**Слой интеграций РЕАЛИЗОВАН (Adapter pattern).** Единый интерфейс CRMAdapter,
данные приводятся к унифицированным моделям (UnifiedLead, UnifiedDeal, CTInteraction).
Уже работают на РЕАЛЬНЫХ данных:
- **Bitrix24Adapter** (через входящий вебхук): лиды, сделки, справочник стадий;
- **CalltouchAdapter**: журнал звонков;
- подключение и проверка — через веб-панель (карточка клиента → «Интеграции»);
- **маппинг стадий** портала клиента настраивается в панели (стр. «Настроить стадии CRM»)
  и хранится в таблице `stage_mappings`;
- агенты `leads.py` и `finance.py` уже используют реальные данные CRM, `leads.py` —
  полную сверку Calltouch↔CRM, если подключены оба.

Добавить amoCRM/RetailCRM = написать ещё один класс-адаптер в `app/integrations/`,
реализующий интерфейс CRMAdapter, и зарегистрировать его в `service.build_crm_adapter`.
Агенты трогать НЕ нужно. Демо-данные остались только как запасной режим: если
интеграция у клиента не подключена, агент честно сообщает об этом и показывает
пример вместо реальных цифр.

## ПРИНЦИПЫ, КОТОРЫЕ НЕЛЬЗЯ НАРУШАТЬ

1. **LLM только для языка.** Сверки, публикацию, расчёты — кодом, без нейросети.
2. **`app/llm.py` — единственное место выбора модели.** Агенты не знают, какая
   модель под капотом (это как шлюз LiteLLM). Не хардкодить модель в агентах.
3. **Согласование человеком** перед любой публикацией. Ничего не публикуется автоматом.
4. **Секреты только в `.env`**, никогда в коде и не в Git.
5. **Ошибки не проглатывать молча** — если публикация/интеграция упала, это должно
   быть видно в панели и/или уведомлением, а не выглядеть успехом.
6. **Данные и настройки — в БД, не в коде** (ради мультитенантности).

## СТРАТЕГИЧЕСКИЕ ЦЕЛИ (куда движемся — учитывай в каждом решении)

1. **Передача в другие руки.** В итоге систему будет вести НЕтехнический человек
   (маркетолог/оператор), не разработчик. Значит: никаких команд в терминале для
   повседневной работы — вся настройка (клиенты, профиль бренда, контент-план,
   конкуренты, интеграции, расписание, согласование) должна делаться **через
   веб-панель**, максимально просто, с понятными русскими подписями и подсказками.
   Любую новую функцию проектируй так, чтобы ею мог пользоваться человек без ИТ-навыков.
2. **Простота для конечного пользователя.** Интерфейс — чистый и очевидный.
   Сложную «кухню» (API, токены, промпты) прятать под капот и настраивать один раз
   при онбординге, а не заставлять оператора с этим сталкиваться.
3. **Переход на Claude (Anthropic) вместо GigaChat.** В перспективе основная LLM —
   Claude (лучше качество текстов). Менять ТОЛЬКО в `app/llm.py` (это единая точка):
   добавить ветку с `langchain-anthropic` (класс `ChatAnthropic`). Приоритет выбора
   модели оставить настраиваемым (Claude / GigaChat / Ollama), чтобы переключать без
   переписывания агентов.
4. **Гибкая оплата.** Хостинг и сервисы должны оплачиваться не только картой ЕС, но и
   другими способами (карта РФ, крипта, PayPal и т.п.). Это критерий выбора будущего
   хостинга и платных API.
